## 2026-09-17 - the page is generated, and every claim on it is a binding

**RST-A3.** The profile page is the first URL a reviewer opens and it was blank. It is now
a positioning statement and one card per public repository, generated by
`scripts/render_readme.py` from `profile.yaml`.

**Why generated rather than written.** Two reasons, and the second is the one that
matters.

Adding a repository has to be adding a row, not rewriting a page. A layout that must be
re-laid out every time the estate grows stops being maintained, and the cards then drift
from what the repositories contain. `abyss-write-gate` is already known to be coming; it
costs four lines of `profile.yaml` and touches nothing else.

More importantly, a generated page is a page whose claims pass through one shape. Every
card names at least one binding - a command, a gate identifier, or a committed artifact -
with the path in the target repository that has to exist for the claim to mean anything.
`tests/test_rst_a3_...` resolves every one of them against the live repository. A card
written by hand could say anything; a card rendered from a binding cannot.

**Why the card set is read from the account rather than kept here.** A list kept here is a
list that goes stale the day a repository goes public. The check reads
`api.github.com/users/malex4hire/repos` and compares, so a repository with no card is a
gap the check finds rather than one somebody has to remember. The profile repository
itself is excluded, declared in the check rather than filtered quietly.

**Why the checks run on a schedule as well as on push.** The page makes claims about
repositories that change after it is written. A check that only runs when the page is
edited cannot catch a command renamed somewhere else. Weekly, because these repositories
move slowly and a daily job for a weekly signal is a standing bill with no product.

**Why superlatives are refused outright.** A superlative is unbound by construction: there
is no file that proves "best". The vocabulary is declared in the check, and the honest
reading of "no unbound superlative" is that there is no bound one either.

**Why the network failure is loud.** These checks resolve claims against live
repositories. Where the network is unreachable they fail with a named reason rather than
skipping, because a check that goes quiet when its input is missing is the shape the page
is trying not to be.

## 2026-09-17 - one commit per constraint, and the history is an input

**RST-A4.** `tests/test_rst_a4_...` derives the set of constraints from this repository's
own `tests/test_rst_*.py` files and reads commit subjects, so a check that arrives with no
commit naming it fails, and so does a branch collapsed into one commit claiming all of
them.

It reads history rather than a branch range against `origin/main`, because a range is
empty the moment the branch merges and the check would then be green forever for the wrong
reason. `actions/checkout@v4` fetches one commit by default, so the workflow sets
`fetch-depth: 0`.
